# AgentsOffice 像素人物交互动画整理与规划

> 最后更新：2026-04-03

## 1. 文档目标

本文档用于整理 AgentsOffice 当前像素人物已具备的动画能力，并规划后续可用于交互反馈、状态表达、协作演出的人物动画方案。

目标不是一次性引入大量复杂动作，而是在现有 Phaser 场景、角色精灵表和 EventBus 机制的基础上，逐步补齐一套可扩展、可复用、可事件驱动的交互动画规范。

---

## 2. 当前已实现的动画与交互反馈

当前人物交互逻辑主要集中在 `frontend/src/phaser/scenes/OfficeScene.ts`，已具备的表现能力如下。

### 2.1 已实现的角色动画

| 分类 | 名称 | 方向数 | 实现方式 | 当前用途 |
| --- | --- | --- | --- | --- |
| 帧动画 | `idle` | 4 方向 | 单帧朝向切换 | 静止朝向展示 |
| 帧动画 | `walk` | 4 方向 | 6 帧循环 | 人物移动时播放 |
| Tween 动画 | `idleMotion` | 无方向差异 | 上下轻微浮动 | 人物站立时增加生命感 |
| Tween 动画 | `workingMotion` | 无方向差异 | 左右微摇 + 缩放 | 表示角色处于工作中 |
| UI 动画 | `bubble fade in/out` | 无方向差异 | 透明度渐变 | 角色说话时显示头顶气泡 |
| 交互反馈 | `hover tint` | 无方向差异 | Sprite 着色 | 鼠标悬停高亮 |

### 2.2 已实现但不属于独立动作帧的交互

| 交互 | 当前反馈 | 备注 |
| --- | --- | --- |
| 点击人物 | 触发 `agent:clicked` 事件 | 无点击专属动作 |
| 人物移动到房间 | 自动寻路 + 播放 `walk` | 已具备基础演出能力 |
| 工作状态变化 | `agent:status` 驱动工作抖动 | 已可映射更多状态 |
| 对话输出 | 头顶气泡出现/消失 | 已有最基本“说话中”反馈 |

### 2.3 当前缺失的关键交互动画

以下类型目前尚未形成明确动作定义：

- 点击确认动作
- 对话中动作
- 接收任务动作
- 完成任务动作
- 出错/困惑动作
- 欢迎/打招呼动作
- 协作会面动作
- 与场景物件联动动作
- 转场类演出动作

### 2.4 当前实现存在的问题

除“动画数量不足”之外，当前实现本身还存在以下几个已知问题，后续应优先修正，否则新增交互动画会建立在不稳定的基础上。

#### 问题 1：人物初始渲染观感异常，底部阴影/落脚感不一致 ✅ 已修复

现象：

- 角色刚渲染出来时，落地感不统一。
- 不同人物看起来像站在不同高度。
- 有的人物脚底区域更厚，有的人物像悬空或陷入地面。

当前代码现状：

- 角色只创建了一个 `sprite` 和一个 `nameTag`，没有独立的“脚底阴影”对象。
- 人物统一使用 `sprite.setOrigin(0.5, 1)`，即以精灵底部中心作为锚点。
- 所有人物都直接按房间点位 `container(pos.x, pos.y)` 放置，没有对不同素材做基线矫正。

结论：

- 当前“底部阴影不一致”并不是场景里单独画了不一致的阴影，而更可能是 **角色素材本身的底部留白、脚底投影、基线位置不统一**，再叠加统一锚点策略后导致的视觉偏差。
- 由于没有单独的脚底阴影层，场景也无法对角色落地感做统一控制。

影响：

- 角色站位显得不专业。
- 同一房间内多个角色会出现“有人漂浮、有人下沉”的观感。
- 会放大后续移动动画和交互动画的不协调感。

建议修复方向：

1. 为角色增加统一的脚底阴影层，例如椭圆阴影或小型 shadow sprite。
2. 引入每个角色素材的 `footOffsetY` 或 `baselineOffsetY` 配置，允许按 spriteKey 微调基线。
3. 在真正修动作前，先校准 `idle` 默认帧的落地位置。

#### 问题 2：人物移动动画与实际素材不匹配 ✅ 已修复

现象：

- 人物移动时的动作明显不自然，甚至看起来像播错了动作。
- 行走方向与肢体动作的对应关系不稳定。
- 当前移动反馈更像“角色在平移，顺便播放了一组不准确的帧”。

当前代码现状：

- 行走动画完全依赖硬编码：
  - `IDLE_ROW = 1`
  - `WALK_ROW = 2`
  - 每个方向固定取连续 `6` 帧
  - 方向起点固定为 `0 / 6 / 12 / 18`
- 这意味着当前代码默认所有人物精灵表都满足“同一布局、同一行定义、同一方向顺序”的前提。

结论：

- 当前移动动画逻辑不是根据素材元数据解析出来的，而是基于固定假设直接取帧。
- 只要角色表实际布局不是“第 2 行就是 walk、每方向连续 6 帧、方向顺序 down/right/up/left”，动画就会播错。
- 从目前表现来看，这套硬编码布局与现有角色素材并不完全匹配，因此用户看到“移动动画完全不对”是符合代码现状的。

影响：

- 角色移动缺乏可信度。
- 后续再做 `greet`、`receiveTask`、`completeTask` 等动作时，会继续受到基础动作错误的拖累。
- 用户会误以为整个角色系统都不稳定。

建议修复方向：

1. 先重新确认角色精灵表真实布局，至少明确 idle、walk、各方向的帧区间。
2. 将 `IDLE_ROW`、`WALK_ROW`、方向起点、每方向帧数从硬编码改为配置化。
3. 如果不同角色素材布局不完全一致，则应支持按 `spriteKey` 单独定义动画映射。
4. 在修复帧选择前，不建议继续叠加新的帧动画。

#### 问题 3：提交任务后的人物移动逻辑不够直观，目的地取决于后端事件

用户关心的问题：

- 提交任务后角色为什么会移动？
- 具体会移动到哪里？
- 是固定规则，还是随机的？

当前逻辑链路：

1. `ChatBox` 在接收流式事件时，如果消息里带有 `movement`，就会发出 `chat:agent-move`。
2. `OfficeScene` 监听 `chat:agent-move`，调用 `moveAgentToRoom(agentId, roomId)`。
3. `moveAgentToRoom()` 会把角色移动到目标房间的某一个 `spot` 点位。
4. 点位不是精确业务目标，而是“该房间预设站位列表中的一个空位”。

当前规则总结：

- 调度员在路由消息里通常停留/回到 `manager`。
- 普通 Agent 在开始使用工具时，会被标记移动到 `datacenter`。
- 普通 Agent 在工具调用结束并生成最终回复后，如果本轮确实用过工具，会再移动回自己的 `homeRoom`。
- 如果某轮没有触发工具调用，则通常不会触发这段“去数据仓库再返回”的移动演出。

这意味着：

- 当前任务移动逻辑本质上是 **后端业务事件驱动的房间切换演出**，不是前端自主推断。
- 它表达的是“开始查资料/调用工具 -> 去数据仓库；完成后 -> 回自己的工位”。
- 这套规则有一定可解释性，但在前端界面上缺少显式说明，因此用户会觉得“人物为什么突然跑过去”不够直观。

现有问题：

- 没有视觉提示告诉用户“去 `datacenter` 是在执行工具/查库/处理数据”。
- 房间移动和任务类型耦合不够细，例如所有用工具的 Agent 都去 `datacenter`，语义过于单一。
- 到达房间后只是站到空位，没有与场景物件建立操作关系。

建议修复方向：

1. 给“去数据仓库”增加状态提示，例如头顶图标、过程消息或房间语义说明。
2. 将移动目标从“统一去 `datacenter`”升级为“按任务类型去不同功能区”。
3. 让角色到达后与具体物件发生联动，例如面向屏幕、面向会议桌、面向展板。

#### 问题 4：人物当前几乎没有与其它场景元素交互的能力

现象：

- 角色现在可以移动、显示气泡、响应点击。
- 但与办公室里的桌子、看板、设备、会议桌、展示区等元素没有真正的交互关系。

当前代码现状：

- 场景中创建了 tilemap 可视层和碰撞层，但没有为办公物件建立可交互对象。
- 目前 `setInteractive()` 只绑定在人物 `container` 上。
- 没有发现物件级事件，例如 `object:clicked` 的落地实现。
- 角色移动到房间后，也没有“面向某个物件执行动作”的后续逻辑。

结论：

- 当前角色交互能力主要是“角色对用户有响应”，还不是“角色对场景世界有行为”。
- 也就是说，现在的人物更像可点击的状态节点，而不是会使用办公室设施的角色。

影响：

- 房间的功能语义较弱。
- “去会议室”“去数据仓库”“去展示厅”这些移动，更多只是位置变化，而不是行为变化。
- 会限制后续协作演出和沉浸感提升。

建议修复方向：

1. 为关键物件建立交互锚点，例如大屏、会议桌、展板、工位电脑。
2. 角色到房间后，不只占据房间空位，还应绑定一个面向目标物件的操作点。
3. 增加 `object:clicked`、`agent:interact-object` 一类事件，为人物和场景元素联动打通机制。
4. 后续动画规划中的 `inspectScreen`、`present`、`discuss` 等动作，应以“角色 + 场景物件”联合演出为目标。

## 3. 现有资源约束

根据当前实现，可确认的技术边界如下：

- 角色精灵表当前通过 `PreloadScene` 以 `32x64` 尺寸切帧加载。
- 当前动画注册逻辑只使用了 `idle` 行与 `walk` 行。
- 动画播放入口已经统一收敛在 `playAgentAnimation()`。
- 状态驱动入口已经存在于 `agent:status`、`chat:agent-bubble`、`chat:agent-move` 等事件。
- 现有系统已经支持用 Tween 补足“没有额外帧素材”的交互反馈。

这意味着后续规划应分两条线并行推进：

1. **低成本路线**：优先增加基于 Tween、气泡、图标、粒子和小幅位移的交互反馈。
2. **中成本路线**：当角色精灵表中确认存在更多动作行，或后续新增人物素材时，再补充真正的动作帧动画。

## 4. 可用于交互的动画体系规划

建议将人物动画拆成四层，避免所有反馈都挤在一套动作帧里：

| 层级 | 类型 | 说明 | 优先级 |
| --- | --- | --- | --- |
| L1 | 基础角色动作 | 待机、行走、转身、工作 | P0 |
| L2 | 状态表达动作 | 思考、说话、完成、报错、等待 | P0 |
| L3 | 交互确认动作 | 点击响应、接任务、打招呼、挥手 | P1 |
| L4 | 协作演出动作 | 两人会面、围桌讨论、指向物件、围观屏幕 | P2 |

## 5. 推荐交互动画清单

### 5.1 P0：优先补齐的基础交互动画

这部分应优先做，因为它们直接影响用户能否看懂角色当前状态。

| 动画名 | 触发时机 | 建议实现方式 | 价值 |
| --- | --- | --- | --- |
| `turnToTarget` | 点击人物、收到事件时 | 仅切换朝向，不必新增帧 | 让角色“有反应” |
| `think` | Agent 推理中 | 头顶省略号/灯泡图标 + 轻微停顿 | 区分空闲与思考 |
| `talk` | Agent 输出文本时 | 气泡 + 微缩放脉冲 | 强化说话感 |
| `receiveTask` | 调度员分发任务后 | 轻微上跳 + 高亮描边 | 表达“收到任务” |
| `completeTask` | Agent 完成任务时 | 上浮勾号/星星 + 短暂庆祝 | 表达“完成” |
| `error` | 执行失败时 | 左右快速抖动 + 红色提示图标 | 表达异常 |
| `standby` | Agent 不活跃/待命 | 降低饱和度或半透明 | 区分在线但未投入工作 |

### 5.2 P1：增强沉浸感的交互动画

这部分用于让人物更像“办公室成员”，适合在基础状态反馈稳定后加入。

| 动画名 | 触发时机 | 建议实现方式 | 备注 |
| --- | --- | --- | --- |
| `greet` | 用户首次点击人物、角色靠近用户关注区域 | 挥手或点头；无帧时可做上跳 + 气泡 | 提升亲和力 |
| `confirm` | 保存配置、接受指令、确认操作 | 点头感 Tween + 对勾图标 | 替代纯文字反馈 |
| `reject` | 无法执行或权限不足 | 左右摇头 + 提示气泡 | 与 `error` 区分 |
| `surprised` | 被临时调度、收到紧急任务 | 短促后仰 + 感叹号 | 用于事件性演出 |
| `focus` | 长时间工作中 | 轻微前倾 + 循环节奏 | 比当前 `workingMotion` 更稳定 |
| `celebrate` | 多 Agent 协作成功 | 小幅挥手/鼓掌/闪光 | 用于关键完成节点 |

### 5.3 P2：面向办公室叙事的协作演出动画

这部分更偏“产品演出”，适合在工作流、任务协同、场景物件交互成熟后实现。

| 动画名 | 触发场景 | 建议实现方式 |
| --- | --- | --- |
| `meet` | 两个 Agent 在同一房间汇合 | 先转向彼此，再弹出双向气泡 |
| `discuss` | 协作室开会 | 围绕会议桌站位 + 轮流气泡 |
| `present` | 展厅讲解/汇报 | 角色朝向看板，气泡与面板联动 |
| `inspectScreen` | 数据仓库看大屏 | 角色朝向屏幕，头顶出现图表图标 |
| `handoff` | 任务交接 | A 完成后转向 B，B 触发接收动作 |
| `escortUserFocus` | 用户切到某模块 | 角色移动到对应区域并指向目标 |

## 6. 动画触发规则建议

建议后续以“状态事件 + UI 事件 + 场景事件”三类源头驱动动画。

### 6.1 状态事件驱动

| 事件/状态 | 建议动画 |
| --- | --- |
| `idle` | `idle` + `idleMotion` |
| `working` | `focus` 或当前 `workingMotion` |
| `thinking` | `think` |
| `speaking` | `talk` + 气泡 |
| `completed` | `completeTask` |
| `error` | `error` |
| `standby` | `standby` |

### 6.2 用户交互驱动

| 用户操作 | 建议动画 |
| --- | --- |
| 点击人物 | `turnToTarget` + `confirm` 或 `greet` |
| 悬停人物 | 保留 `hover tint`，可叠加呼吸描边 |
| 打开人物面板 | 人物面向镜头或朝向右侧面板 |
| 派发任务 | `receiveTask` |
| 手动移动房间 | `walk` + 到达后 `turnToTarget` |

### 6.3 协作事件驱动

| 业务事件 | 建议动画 |
| --- | --- |
| 调度员分配任务 | 调度员 `talk`，目标角色 `receiveTask` |
| Agent 间协作 | 双方 `meet` 或 `handoff` |
| 上传数据完成 | 数据工程师 `completeTask` |
| 报表生成完成 | 数据产品经理 `present` |

## 7. 推荐实现策略

### 7.1 动画实现分层

建议将交互动画实现拆成三种手段：

| 手段 | 适用场景 | 成本 | 说明 |
| --- | --- | --- | --- |
| 帧动画 | 行走、挥手、鼓掌、坐下等强动作 | 中 | 依赖精灵素材是否支持 |
| Tween 动画 | 点头、抖动、浮动、放大缩小 | 低 | 适合快速补齐反馈 |
| UI/VFX 叠层 | 图标、气泡、粒子、描边、状态标识 | 低 | 与角色动作解耦，最易扩展 |

### 7.2 统一行为逻辑方案

如果要让角色行为与当前地图场景真正一致，建议后续不要再把“任务处理逻辑”继续收敛成写死的 `room_id` 切换，而是升级为统一的人物行为模型。

目标逻辑如下：

1. 待机时，角色会在自己的活动区域内轻量随机走动，而不是永远站桩。
2. 空闲阶段，角色可以短暂走向附近的场景元素，例如电脑桌、白板、公告牌或会议桌，形成弱交互。
3. 接收到任务时，角色应先进入“接单”状态，再移动到明确的工作锚点，而不是仅仅移动到某个房间空位。
4. 到达工作锚点后，角色要面向目标物件，并与椅子、电脑、大屏或桌面形成可解释的工作状态。
5. 工作完成后，角色应退出工作状态，并返回默认工位或进入下一轮待机行为。

推荐的人物状态流转：

| 阶段 | 状态名 | 含义 |
| --- | --- | --- |
| 待机阶段 | `idle` | 原地待机、轻微浮动 |
| 自主行为阶段 | `wander` | 在约束区域内随机走动 |
| 场景弱交互阶段 | `ambient_interact` | 与附近场景元素发生短暂交互 |
| 接单阶段 | `receive_task` | 收到任务，做出确认反馈 |
| 寻路阶段 | `move_to_anchor` | 前往具体工作锚点 |
| 工位交互阶段 | `work_at_anchor` | 面向电脑桌/椅子/屏幕执行工作动作 |
| 完成阶段 | `complete_task` | 输出完成反馈 |
| 回落阶段 | `return_to_idle` | 回工位或回待机状态 |

这套模型的关键点不在于“去哪个房间”，而在于以下三层语义：

- **行为意图**：当前是待机、接单、工作、完成还是巡游
- **目标锚点**：当前去的是哪一个具体物件点位，而不是一个笼统房间
- **表现效果**：到达后播放什么动作、朝向哪里、和哪个物件联动

### 7.3 地图与交互锚点建议

为了支撑统一行为逻辑，地图层需要引入“交互锚点”概念。推荐优先定义以下锚点类型：

| 锚点类型 | 用途 | 示例 |
| --- | --- | --- |
| `idle_anchor` | 默认站位或回归点 | 每个 Agent 的默认工位 |
| `work_anchor` | 工作时站位 | 电脑桌前、工位前 |
| `chair_anchor` | 椅子关联点 | 椅子前方或坐姿预留点 |
| `screen_anchor` | 面向屏幕点 | 数据仓库大屏前 |
| `meeting_anchor` | 协作站位 | 会议桌周围 |
| `board_anchor` | 展示/汇报点 | 展厅讲解板前 |
| `ambient_anchor` | 待机弱交互点 | 公告栏、白板、咖啡角 |

每个锚点至少应具备：

- 坐标
- 默认朝向
- 所属房间/区域
- 物件类型
- 是否可占用
- 是否允许待机时随机访问

### 7.4 推荐优先方案

建议先不要等待新人物素材，而是先在当前架构上落地以下能力：

1. 扩展人物状态枚举，明确区分 `thinking`、`speaking`、`completed`、`error`。
2. 为每种状态定义一个统一动画入口，例如 `playAgentEffect(agent, effectName)`。
3. 保持 `idle/walk` 继续走精灵帧，新增交互优先走 Tween 和图标层。
4. 将气泡、图标、状态圈、粒子统一挂在人物 `container` 上，避免散落在场景层。
5. 保证不同效果可叠加，但同类效果互斥，例如“工作抖动”和“错误抖动”不能同时存在。
6. 将“移动目标”从房间空位逐步升级为“地图交互锚点”。

### 7.5 推荐代码结构

后续可考虑拆出独立模块，而不是继续全部堆在 `OfficeScene.ts`：

| 模块 | 职责 |
| --- | --- |
| `agentAnimationRegistry.ts` | 注册所有动作名与播放规则 |
| `agentEffects.ts` | 管理 Tween、图标、粒子、气泡 |
| `agentStateMachine.ts` | 维护状态切换与动画互斥关系 |
| `agentInteractionEvents.ts` | 统一收口点击、悬停、派发、完成等事件 |

## 9. 分阶段落地计划

### Phase 1：状态可读性增强

目标：先让用户一眼看懂每个 Agent 正在做什么。

- 补充 `thinking`、`speaking`、`completed`、`error` 四类状态表现
- 保留现有 `idle`、`walk`、`workingMotion`
- 新增状态图标层和简易脉冲/抖动/上跳 Tween
- 不依赖新增角色素材

### Phase 2：点击与任务交互增强

目标：让人物对用户操作和系统调度有明确“回应”。

- 点击人物后触发 `greet` 或 `confirm`
- 调度员派单时目标角色触发 `receiveTask`
- 完成任务时触发 `completeTask`
- 面板打开时人物自动朝向目标区域

### Phase 3：多 Agent 协作演出

目标：把“多 Agent 协作”从文字日志升级成可视化办公室行为。

- 两人会面
- 房间讨论
- 任务交接
- 面向看板汇报
- 朝特定办公物件进行操作反馈

## 10. 建议的动画命名规范

建议统一采用以下命名方式，避免后续混乱：

| 类型 | 命名示例 |
| --- | --- |
| 帧动画 | `char_08-idle-down`、`char_08-walk-right` |
| 角色效果 | `effect-think`、`effect-complete` |
| 交互动作 | `action-receive-task`、`action-greet` |
| 协作演出 | `scene-meet`、`scene-handoff` |

统一原则：

- `idle`、`walk` 只保留为底层动作态
- 与业务相关的短时反馈统一归类为 `effect-*`
- 有明确起止过程的动作统一归类为 `action-*`
- 涉及多人的编排统一归类为 `scene-*`

## 11. 最小可执行方案（推荐）

如果只做一轮低成本升级，建议先实现以下 6 项：

1. `think`：头顶省略号图标 + 轻微停顿
2. `talk`：气泡出现时人物做轻微脉冲
3. `receiveTask`：收到任务时上跳一次
4. `completeTask`：完成时勾号或星星上浮
5. `error`：红色感叹号 + 短促抖动
6. `turnToTarget`：点击后转向用户关注方向

这 6 项都可以在不替换当前角色素材的前提下完成，并且能显著提升“角色真的在工作”的感知。

## 12. 结论

当前 AgentsOffice 已经具备人物动画系统的基础骨架，但仍处于“可移动、可说话、可高亮”的基础阶段。后续最值得优先补齐的不是更复杂的走路帧，而是能够表达 **思考、接单、完成、异常、回应用户** 的交互反馈。

推荐路线是：

1. 先用 Tween + 图标 + 气泡完善状态反馈。
2. 再补点击确认和任务派发演出。
3. 最后再做多 Agent 协作场景化动画。

这样既能快速提升产品表现力，也不会被角色素材是否充足卡住开发节奏。
